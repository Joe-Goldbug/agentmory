# AI Product + Code Iteration Memory

本文件定义了针对产品从想法（Idea）到规模化（Scale）的四大阶段迭代模型，并为 AI 编码助手（Claude Code, Codex 等）设立了安全边界和运行提示词。

---

## 一、核心操作模型 (Core Operating Model)

我们拒绝让 AI 盲目进行全盘开发。人和 AI 的分工非常明确：
* **人类主导**：决定 目标 (Goal)、边界 (Boundary)、优先级 (Priority) 和 验收标准 (Acceptance Criteria)。
* **AI 协助**：验证假设、拆解工作任务、执行受控动作、测试验证、回报风险与下一步。

一次只做一件清晰的事情。每轮任务结束后，写回进展、决策、风险和下一步。

---

## 二、四阶段迭代工作流 (Four-Phase Iteration Workflow)

### Phase 1: Idea (想法阶段)
* **目标**：在写代码之前，必须证明问题是真实存在的。
* **AI 底座角色**：**Skeptical Product Advisor (怀疑论产品顾问)**。默认不附和用户，挑剔假设、辨别虚假需求、对比现有竞品，并在写代码前给出最小化验证行动。
* **分析模板**：
  1. 谁遇到了这个痛点？
  2. 这个痛点发生的频率如何？有多痛？
  3. 用户今天是如何解决这个痛点的？
  4. 为什么现有的其他方案不够好？

### Phase 2: MVP (最小可行产品阶段)
* **目标**：只构建最核心的闭环，让真实用户能完成一个核心价值行为。
* **边界原则**：在动手前，以表格形式清晰界定“本版本必须构建的模块”和“本版本明确不构建的模块”。
* **工程原则**：不一次性编写大型架构，拆解为多次微小且可完全验证的代码变更。

### Phase 3: Launch (上线阶段)
* **目标**：度量用户激活、留存、反馈以及系统的稳定性，不以“代码写完”作为上线标准。
* **度量指标**：
  - **Activation (激活)**：用户是否完成了第一个核心操作。
  - **Retention (留存)**：第 7 天和第 30 天用户是否留存。
  - **Stability (稳定性)**：报错率、加载速度、网络耗时、发布健康度。

### Phase 4: Scale (规模化阶段)
* **目标**：把之前重复依靠人肉判断的经验提炼为自动化的产品规则、技术规则和运营规范。

---

## 三、硬性工程边界 (Engineering Boundaries)

1. **写代码前**：必须阅读相关文件的真实实现，阐明本次修改具体解决什么、不解决什么。
2. **写代码中**：仅改动必须修改的部分，严禁对无关文件做预防性重构或清理。
3. **写代码后**：必须通过编译、静态检查、真实测试命令或页面实际行为证明结果，严禁仅凭口头猜测或主观推断。
