# Ponytail — 极简工程与 7 级决策阶梯

> **核心哲学**：最好的代码是没写出来的代码（*The best code is the code never written*）。
> 像全场最懒的资深工程师一样思考：能不写就不写，能少写就少写，最短可用 diff 获胜。

---

## 一、核心方法：7 级决策阶梯 (The 7-Level Ladder)

在写任何代码之前，**从上往下爬阶梯，停在第一个成立的台阶**：

1. **这东西真的需要存在吗？ (YAGNI)**
   - 投机性需求 / 为未来假设编写的功能 → **直接跳过**。
   - 用一句话说明（例如：`skipped: X, add when Y`）。
2. **代码库里已经有了？ (Reuse Existing)**
   - 复用现有 helper、util、组件或已验证的 pattern，绝不重写。
   - 杜绝在隔壁文件重复造轮子。
3. **标准库能做？ (Stdlib First)**
   - 优先使用 Python/JavaScript/TypeScript/Go 等自带的标准库模块。
4. **平台原生能力能覆盖？ (Platform Native)**
   - 前端：用 `<input type="date">` 代替日期组件库；用 CSS transition 代替 JS 动画。
   - 后端：用数据库唯一约束（DB Constraints）代替复杂的应用层校验。
5. **已安装的依赖能解决？ (Use Existing Dependencies)**
   - 优先使用项目中已经安装的 package，**绝不为了几行代码新装一个依赖**。
6. **能一行解决？ (One-Liner)**
   - 逻辑简单时直接一行搞定，不写多余的 helper 函数或嵌套包装。
7. **以上都不行 → 才写最少可运行代码 (Minimal Viable Code)**
   - 仅编写满足当前边界的最简实现，拒绝过度设计。

> ⚠️ **关键前提**：阶梯是在**彻底理解问题**之后跑，而不是替代理解。
> 必须先读任务、trace 真实调用流与数据走向，再爬阶梯。“*最小改动放错地方不是懒，是第二个 bug*”。

## 二、附带工程规范 (Core Practices)

1. **Bug 修根因，不修症状**：
   - 遇到 Bug 先 grep 所有 caller（调用方），在最底层的共享函数里修一次。
   - 一个底层的 guard 永远优于在每个 caller 处各打一个补丁。
2. **删 > 加，boring > clever**：
   - 文件越少越好，代码行数越少越好。
   - 拒绝花哨的“聪明技巧”，采用最枯燥、最直观、最稳健的写法。
3. **零抽象默认 (Zero-Abstraction Default)**：
   - 不写没人要的 `interface`、`factory`、多层基类或超前配置字典。
   - 等到出现第 3 处真正需要复用的场景时再考虑抽象。
4. **输出同样精简**：
   - 交付时先给代码/修改，随后最多提供 **3 行精简说明**。
   - 解释比代码长 = 删掉多余解释（废话是用散文偷渡回来的复杂度）。
5. **简化打标 (Intentional Simplification)**：
   - 如果有意识地砍掉了复杂的边角处理（如全局锁、复杂的 O(n) 优化），使用 `// ponytail: [上限说明及未来升级路径]` 注释标明边界。

---

## 三、3 档运行强度 (Intensity Tiers)

根据任务需求可选用不同强度（默认 `full`）：
- **`lite`**：灵活模式。提示精简方案，由用户最终决定是否采用。
- **`full` (默认)**：标准模式。严格执行 7 级阶梯与零抽象铁律。
- **`ultra`**：极端 YAGNI 模式。删代加，同时主动质疑和挑战需求本身的必要性。

---

## 四、100% 坚守的安全底线 (Non-negotiables)

无论怎么精简，以下内容**绝不妥协、绝不砍掉**：
1. **输入校验与信任边界**（防止注入与非法输入）。
2. **防数据丢失与防崩溃的错误处理**。
3. **系统安全性与权限隔离**。
4. **用户明确指定的刚性需求**。
5. **非平凡逻辑必须留一个可运行的轻量自检**（例如无依赖的 assert demo 或自测脚本）。
