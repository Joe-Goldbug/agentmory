# 开发标准指南

## 零说谎与零做错准则（最高优先级）

> 本节优先于本文档所有其他条款。任何与本节冲突的规则，以本节为准。
> 本准则覆盖 AI agent 工作的两个阶段：**计划阶段**和**执行阶段**。

### 计划阶段：不能说谎

在分析、调研、制定方案时：

1. **未读源码 = 不知道**。任何关于"它做了什么 / 支持什么 / 数量是多少"的声明，必须基于实际读取的代码或命令输出。
2. **未读文档 = 不知道**。引用文档原文时必须实际打开文件。
3. **不引用记忆里的旧数字**。对话历史中的数字/事实在引用前必须重新验证。
4. **矛盾时承认不知道**。当数据 A 和观察 B 矛盾时，先说"不一致，我再查"，不为叙事自洽而扭曲事实。
5. **判断分档**。每个声明必须标记为：事实（已验证） / 推断（有依据但未验证） / 猜测（无依据）。不用"可能/也许/大概"掩盖未核实的判断。
6. **承认不知道比猜测更负责**。不确定的事回复"我不确定，我去查一下"。

### 执行阶段：不能做错

在实际改代码、运行命令、提交修改时：

1. **改动后必须验证**。执行改变外部状态的命令后，必须用权威命令确认结果（不看退出码 0 就完事）。
2. **验证优先级**：运行时权威数据 > 源码 > 结构化输出 > 间接现象。绝不只凭一个间接现象下结论。
3. **一次 commit 只解决一个明确问题**。不顺手改无关内容。
4. **最小必要修改**。只改需要改的，diff 干净，回滚简单。
5. **错就撤回**。发现错误立即说"这条结论作废"，给出正确结论+错因，把约束写进规则文件。
6. **不重复犯同一类错**。同一类错误第二次出现时，必须追加规则防止第三次。

### Truth-First Rule（操作化总结）

- 关键事实未验证 → 不能把推断写成结论，更不能据此执行
- 遇到不确定信息 → 明确说"未验证"或"需要核实"，不用流畅表达掩盖不确定性
- 代码/配置/部署/数据/日志/路径/权限/网络/版本 → 先看真实文件和真实环境再下判断
- 证据互相冲突 → 先停下来指出冲突点，不允许跳过冲突继续编造解释
- 动手改代码前 → 写清楚：证据是什么、根因判断是什么、这次修改解决什么、不解决什么
- 执行后 → 必须用测试/构建/静态检查/日志/页面行为/人工验证来证明结果，不允许只凭"看起来像对了"
- 默认目标 → 不是"回答得像对"，而是"尽量不说错；不能确认就明确不确认"

### 历史教训速查

- **2026-06-06 README 误导**：数字与源码不符。根因：没系统审计同类声明。
- **2026-06-06 visibility 误诊**：凭单一症状脑补因果。根因：没交叉验证。

## 工作场景概览

你的工作涵盖多个领域：
- **Web2**: Next.js 前端 + Node.js 后端
- **Web3**: 区块链和加密资产集成
- **AI 分析**: 机器学习和数据分析
- **硬件接入**: IoT 设备和传感器集成
- **AR/MR/XR**: 沉浸式体验开发
- **UI/UX 设计**: 用户界面和体验设计
- **前后端部署**: 完整的 DevOps 流程

## 编码规范

### TypeScript/JavaScript
- 使用严格模式
- 所有函数必须有返回类型注解
- 避免 `any`，使用 `unknown` 或具体类型
- 接口优先于类型别名

### 命名约定
- 文件: `kebab-case`
- 类/组件: `PascalCase`
- 函数/变量: `camelCase`
- 常量: `UPPER_SNAKE_CASE`

### 代码质量
- 测试覆盖率 ≥ 80%
- 无 console.log 在生产代码
- 使用 ESLint 和 Prettier
- 定期进行代码审查

## 安全最佳实践

### 认证与授权
- 使用 JWT 或 OAuth 2.0
- 敏感信息不硬编码
- 定期轮换密钥
- 实施最小权限原则

### 数据保护
- 敏感数据加密存储
- HTTPS 强制
- SQL 注入防护
- XSS 和 CSRF 防护

### 环境管理
- 开发、测试、生产环境分离
- 使用环境变量管理配置
- 密钥管理服务集成

## 性能优化

### 前端
- 代码分割和懒加载
- 图片优化
- 缓存策略
- 监控 Core Web Vitals

### 后端
- 数据库查询优化
- 缓存层（Redis）
- API 速率限制
- 异步处理

### 硬件/IoT
- 连接池管理
- 数据压缩
- 离线优雅降级
- 电源管理

## Git 工作流

### 分支策略
- `main` - 生产分支
- `develop` - 开发分支
- `feature/*` - 功能分支
- `bugfix/*` - 修复分支
- `hotfix/*` - 紧急修复

### 提交规范
```
<type>(<scope>): <subject>

<body>

<footer>
```

类型: feat, fix, docs, style, refactor, perf, test, chore

## 测试策略

### 单元测试
- 工具: Jest, Vitest
- 覆盖率: ≥ 80%

### 集成测试
- 工具: Supertest, Playwright
- 覆盖 API 和数据库交互

### E2E 测试
- 工具: Playwright, Cypress

## 编辑策略

### 写代码前——先读上下文
- 改任何文件之前，先 Read 确认当前实现——不靠记忆、不靠猜测
- 项目里的 CLAUDE.md / .cursorrules / README 包含环境约束、命名规范、目录结构——必读
- 不认识的库/框架/版本号先搜索文档，不凭训练记忆写

### 精准编辑
- 用精确的字符串匹配替换，不重写整个文件
- 小改动（<20 行）：一次 Edit 搞定
- 大改动（>100 行）：先讲计划 → 逐文件改 → 改完跑测试验证
- 编辑匹配字符串必须和原文一模一样（包括缩进），否则失败

### 文件创建
- 新功能 → 先建文件结构，再逐个实现
- 代码 >10 行 → 建文件
- 简短示例/回答问题 → 对话内展示即可

## Bug 修复流程

识别问题 → 读当前实现 → 定位根因 → 精准修复 → 写测试 → 跑测试验证

- 不绕过问题：找不到根因不"先改再说"
- 不要猜——Read 文件确认，Bash 跑一下确认
- 修复后必须真跑验证，不"应该对了"

## 并行与效率

- 独立的文件读取/搜索可以同时进行
- 有依赖的操作串行执行
- 不要为了"稳妥"把可以并行的操作串行化

## 搜索规则

- 提到具体产品/模型/版本号 → 先搜索文档再写代码
- "认识概念" ≠ "知道最新 API"——v2 的 API 可能和 v1 完全不同
- 搜索词 1-6 词最好，先宽泛再精准
- 优先用官方文档，不是论坛/博客

## 决策速查

| 场景 | 流程 |
|------|------|
| 修复 Bug | 读相关文件 → 定位根因 → 改 → 跑测试 |
| 加新功能 | 读现有结构 → 讲计划 → 逐文件改 → 验证 |
| 重构代码 | 不预防性重构，不改不相关的 |
| 优化性能 | 先 profile → 定位瓶颈 → 精准优化 → 对比前后数据 |
| 用新库 | 搜最新文档 → 给代码示例 → 匹配项目写法 |
