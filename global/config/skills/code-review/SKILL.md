# Code Review — 代码审查执行规范

> **核心原则**：审查是为了让代码更好，不是为了证明作者有问题。
> 每条评论必须有具体理由，每个问题必须指向可操作的改进。

---

## 一、执行流程（固定顺序）

在开始写任何评论之前，**先完整走完以下步骤**：

1. **理解上下文**：确认代码的目的、语言、框架、所属模块，以及（如有）PR 描述或变更说明。
2. **整体通读**：先不评论，建立全局印象，识别主要改动路径与数据流。
3. **分类扫描**：按下方五大维度逐项扫描，在脑内分好等级再一次性输出。
4. **输出报告**：按统一格式输出（见第三节），不要边读边随机插入评论。
5. **给出总结评分**：一句话结论 + 可选的 Approve / Request Changes 建议。

---

## 二、五大审查维度与等级

### 维度

| # | 维度 | 关注点 |
|---|------|--------|
| 1 | **正确性** | 逻辑错误、边界条件、类型错误、空指针、并发安全 |
| 2 | **安全性** | 输入校验、SQL/命令注入、敏感信息泄露、权限校验 |
| 3 | **性能** | N+1 查询、不必要的大对象复制、循环内 IO、内存泄漏 |
| 4 | **可维护性** | 命名清晰度、函数职责单一、魔法数字、注释质量 |
| 5 | **测试覆盖** | 关键路径是否有测试、边界值测试、异常路径测试 |

### 严重等级（必须标注）

- 🔴 **BLOCKER**：必须修复才能合并。影响正确性或安全性。
- 🟡 **SUGGESTION**：强烈建议修复，但不阻断合并。
- 🔵 **NITPICK**：风格/命名/小优化，可接受也可忽略。
- ℹ️ **NOTE**：补充说明，无需操作，仅供参考。

---

## 三、输出格式（统一模板）

```
## 代码审查报告

### 总体印象
[1-3 句话描述代码整体质量与主要变更目的]

---

### 问题清单

#### 🔴 BLOCKER

**[文件名:行号]** 问题标题
> 具体问题描述，包括为什么这是个问题。
> **建议**：提供具体的修改方向或示例代码片段。

---

#### 🟡 SUGGESTION

**[文件名:行号]** 问题标题
> 描述 + 建议

---

#### 🔵 NITPICK / ℹ️ NOTE

- `[文件:行]` 小问题描述

---

### 总结

| 维度 | 评价 |
|------|------|
| 正确性 | ✅ / ⚠️ / ❌ |
| 安全性 | ✅ / ⚠️ / ❌ |
| 性能 | ✅ / ⚠️ / ❌ |
| 可维护性 | ✅ / ⚠️ / ❌ |
| 测试覆盖 | ✅ / ⚠️ / ❌ |

**结论**：[一句话结论] → **Approve** / **Request Changes**
```

---

## 四、行为准则

1. **只评论差异**：如用户提供了 diff/PR，只审查变更部分，不对未改动代码展开评论（除非问题与改动直接相关）。
2. **引用原文**：每条问题必须引用具体的文件名 + 行号或代码片段，禁止泛指"这段代码有问题"。
3. **给出建议**：BLOCKER 和 SUGGESTION 必须附带可操作的修改建议，可以是代码示例或明确的方向。
4. **语气中立**：使用"这里可以……"、"建议……"，避免"你写错了"、"这很糟糕"等主观负面措辞。
5. **长度适中**：每条评论不超过 5 行；如需展开讨论，在问题清单后另开一个「延伸讨论」段落。
6. **与 ponytail 协同**：若同时激活了 ponytail skill，对"复杂度过高"类问题优先按 7 级决策阶梯给出极简替代方案。

---

## 五、快速模式（Lite）

当用户说"快速审查"、"粗看一下"或代码 < 50 行时，启用 Lite 模式：
- 跳过 NITPICK 和 NOTE，只输出 BLOCKER 和 SUGGESTION。
- 总结部分只保留"结论"一行，省略维度评分表。

---

## 六、非代码内容

若用户提交的是配置文件（YAML/JSON/Dockerfile/terraform）：
- **正确性** → 语法、必填字段、类型匹配。
- **安全性** → 硬编码密钥、过宽权限、暴露端口。
- **可维护性** → 注释、环境变量化程度。
- 不评价"性能"和"测试覆盖"维度（除非明确相关）。
