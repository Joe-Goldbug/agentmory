## 1. 最新决策与证据边界

产品定位：跨 Agent 统一工作记忆、知识管理与备份系统。服务用户跨工具接续工作、维护有效知识、纠正错误记忆、恢复数据和独立核对历史。

用户提出让 Team 与企业选择“我们公司”或“我们选择的区块链”作为备份方式。本设计将“我们公司”解释为 LWM 产品方托管服务，将“我们选择的区块链”解释为 LWM 筛选并持续验证的去中心化存储后端；单纯提交链上哈希不能算数据备份。企业自有 S3 / 私有存储是另一个可扩展选项。

采用两个主备份模式，允许组合，链上存证独立开关。各模式共用记忆格式、加密与恢复规范，不建立两套互不兼容的知识库。

本版取代旧版以下结论：必须仅面向企业收费、95% / 5% 用户比例、公链是唯一合规方案、自动出具 SOC 2 证书、NFT 自动赋予知识产权、质押保证记忆真实性，以及无来源的收入、市场占有率和性能承诺。

当前仓库功能是否已经落地，应由真实运行及恢复记录判定。本设计不确认“11+ IDE 全部可用”“亚毫秒响应”“永久可用”或任何定价已获市场验证。

## 2. Team 与企业的备份选择

| 模式 | 保存在哪里 | 产品方承担什么 | 客户可获得什么 | 必须说明的限制 |
| --- | --- | --- | --- | --- |
| A：LWM 托管备份 | LWM 管理的远端存储，按公布区域与供应商策略运行 | 服务运维、版本保留、恢复流程、用量与告警 | 简单配置、快速访问历史、可验证恢复 | 服务依赖、区域、保留期限、退出与费用 |
| B：去中心化备份 | LWM 支持名单中的存储网络与实际保存服务 | 加密上传、保存安排、取回监测、续费或归档策略 | 独立于单一 LWM 存储账户的副本与导出路径 | 网络不等于永久、网关可能失败、续费和删除能力各异 |
| A + B：双副本保护 | 两种保存路径 | 统一策略和两份独立状态 | 常用恢复与独立副本兼顾 | 额外成本；两份数据不能共享唯一不可恢复密钥 |
| 企业自有存储：后续扩展 | 客户自己的 S3 / MinIO / 私有环境 | 接入与验证；按合同确定运维职责 | 自有账户、区域和权限控制 | 需要客户配合维护；不自动满足任何特定合规要求 |

建议 Team 默认推荐 A，可选择 B 或 A+B；企业允许按组织和项目指定策略。套餐价格与备份后端分别设计，不把选择去中心化存储强制绑定为 Enterprise。

B 模式必须保存可取回的加密内容及必要清单，不只是 CID、URL 或根哈希。如果后端实际只提供公链交易记录，界面只能称为“链上存证”。

LWM 筛选后端时应核验：真实持久存储机制、地域与可达性、取回耗时、保存期限、费用、删除语义和独立恢复路径。首版支持一个经验证的去中心化后端，不开放任意链地址冒充可用备份。

## 3. 数据存储、密钥与存证分别选择

| 配置轴 | 建议选项 | 说明 |
| --- | --- | --- |
| 数据保存 | A / B / A+B；企业自有存储后续扩展 | 决定数据副本在哪里 |
| 解密控制 | 客户持有；可选明确授权的组织托管恢复 | 决定谁能解密，不由存储地点自动决定 |
| 历史验真 | 签名与完整性检查；可选外部链上锚定 | 决定是否提供独立时间与完整性证据 |

公司托管备份不等于公司可读明文。建议默认客户端加密、客户掌握解密能力；平台主要处理密文和最小必要的运维元数据。企业选择托管恢复或产品方参与解密时，应准确披露访问边界，不能同时宣称“产品方永远不能解密”。

账号登录、备份解密、设备授权和链上签名分开设计。用户通过已授权设备或独立恢复材料解锁新设备。所有恢复材料丢失时不能承诺必定找回。

团队需要组织恢复责任人、成员权限、离职撤销和密钥轮换。撤销成员可以阻止未来访问，不能保证让对方已下载的明文消失。

平台代付只赋予提交已授权存证的能力，不应获得修改记忆或解密备份的权限。

## 4. 交互与模式切换

首次配置：选择组织或项目 -> 选择备份模式 -> 设置区域与保留策略 -> 配置恢复方式 -> 执行首次备份与恢复验证。

日常工作无需钱包弹窗。界面分别展示：工作记忆已发布版本、最近远端保护时间、最近恢复验证时间、各副本健康状态、存证待提交或已确认状态。

模式切换流程：生成目标副本 -> 核对清单 -> 下载、解密与恢复验证 -> 管理员确认新策略生效 -> 按原保留政策处理旧副本。目标验证失败时继续保留原策略；禁止切换过程中先删除唯一可用副本。

链上存证独立于模式：A 可以开启存证，B 也不必额外部署 EVM 合约。底层网络已有的完整性与包含证明先评估能否复用，避免为同一需求重复上链。

团队普通成员不能任意把整个组织记忆上传到公共网络。管理员批准组织范围和预算，后续任务按策略自动执行；例外或新增公开范围才需要再次确认。

## 5. 备份、同步与恢复架构

记忆采集、综合、发布、备份与存证分别管理状态。备份不等待 LLM 分析成功，工作不等待链上出块。

建议流程：授权工作证据 -> 带来源的版本化记忆 -> 一致性导出 -> 持久队列 -> 客户端加密 -> 目标副本 -> 取回校验 -> 独立备份收据 -> 可选签名与批量存证。

同步、备份和记忆合并不可混用：同步传播当前数据，备份保留历史可恢复版本，语义合并处理规则冲突与知识更新。不能靠把同一目录复制到云上替代全部三项能力。

优先评估 Restic 等成熟引擎承担增量去重、加密、快照和恢复，LWM 负责记忆语义和一致性导出。可变备份仓库与不可变长期归档采用不同适配方式。

备份清单至少记录：项目与版本、包含及排除范围、外部原文是否纳入、内容完整性、格式版本和恢复所需依赖。缓存与索引可重建；敏感凭证和设备授权不随普通内容自动恢复。

私有可恢复备份与脱敏共享记忆分开。需要恢复的原文在授权范围内加密保存，不能先改写后仍宣称无损恢复。

增量备份在变更后按策略合并执行，六小时综合整理独立调度；开机或唤醒检查欠账。持久任务有幂等键、退避、预算与失败告警。睡眠、关机及离线期间如实显示远端保护停留时间。

## 6. 区块链证明的准确范围

链上证明核对某份内容是否与历史承诺一致，不能直接证明事实正确、原创、知识产权或法律责任。

优先采用客户端签名和批量锚定：客户端签署版本清单承诺，服务端归并批次根并代付，用户保存签名、包含证明、网络和交易定位信息。提交者地址若是中继，不得当作用户或内容作者。

链上不公开项目名、文件路径、用户身份、凭据和明文。承诺格式需明确版本、序列化、哈希算法和必要随机化。完整性、可取回、解密成功、恢复成功、链上确认分别验收。

IPFS 内容地址不是持续保存保证；Filecoin 保存安排有期限及成本；永久存储也不能保证网关和密钥永远可用。永久上传的密文不能承诺彻底删除，私人工作内容不默认进入永久归档。

Gas 代付不是零成本。账户抽象不是初版必要条件：普通登录、订阅支付与服务端批量中继即可满足许多存证场景。确有用户自主管理链上账户的需求时，再评估 ERC-4337。

## 7. 恢复与平台退出

恢复流程：选版本 -> 获取恢复材料 -> 隔离下载 -> 解密与完整性检查 -> 重建索引 -> 对比当前撤销和权限 -> 预览差异 -> 发布新版本 -> 验证 Agent 真实读入。

保留当前可用状态，不直接覆盖后再校验。恢复旧数据不自动复活已撤销规则、旧设备权限或离职人员授权。无法核验最新撤销状态时标为待核验，不自动启用历史指令。

用户可导出备份目录索引、格式版本、清单、签名公钥与必要证明；解密秘密单独保护。公开格式与独立恢复工具必须能在不调用 LWM 账号服务的情况下处理已授权导出的材料。

B 模式若仅能通过 LWM 网关、账户或唯一密钥取回，不能宣传为独立于 LWM 停服。应验证至少一条独立取回路径，以及平台停服后保存费用由谁持续承担。

订阅取消、账单逾期和供应商退出的保存期限与导出窗口需明确。持久保存需要资源，不能将停服独立恢复等同于无限期免费保存。

## 8. 客户与商业路径

先验证用户实际付出的重复解释、错误规则返工、交接和恢复成本，再扩展市场。

| 顺序 | 客户假设 | 验证问题 |
| --- | --- | --- |
| 1 | 多 Agent 独立开发者 | 是否持续使用；跨工具能否接续；是否为同步与恢复付费 |
| 2 | 小型软件团队 | 交接、权限、项目隔离、成员离开后的知识连续性是否改善 |
| 3 | 与外部客户协作的团队 | 双方签收的版本、测试和交付证据是否值得购买 |
| 4 | 有明确审查要求的企业 | 具体控制、证据导出、部署和支持能否通过客户审查 |

开源免费到团队采购是可测试路径，不是自然发生的增长保证。个人也可以为可靠服务付费。大型企业名称、行业知名度和潜在高客单价不能当成已验证需求。

可按产品版别收费，再按备份容量、保留期限、流量、模型使用和存证额度设套餐。收费覆盖持续维护、恢复演练、版本治理、权限与服务质量，不能只围绕“上传哪条链”。

此前人民币 39 / 89 / 69 元与美元 29 / 199 元等价格均为待测假设，没有正式价格。Enterprise 是否按席位、组织或用量收费，由实际采购和成本验证决定。没有来源的 ARR、毛利率、转化率和恢复速度不作为预测基准。

建议首批 10-20 位目标用户验证激活、留存、真实交接、恢复和支付意愿。试点数量是研究计划，不是市场规模结论。

## 9. 合规与知识产权表述

产品提供供审查使用的证据包，包括来源、版本、授权、验证、签名、完整性和可选链上记录。它不自行出具 SOC 2 鉴证报告，也不承诺免责、法院必然采信或保证专利纠纷结果。

SEC 针对经纪交易商电子记录的相关规则允许 WORM 或符合要求的审计轨迹，并不要求所有记录上公链。不能扩展为所有行业、所有 AI 算法都必须使用区块链。

SOC 2 涉及组织控制的专业鉴证。LWM 只能支持取证与审查，是否满足具体要求需看组织整体控制和专业审查。

USPTO 的相关指引要求发明人为自然人；AI 是辅助工具。时间承诺不自动确立发明人身份、权属或专利优先权。

涉及其他法域、医疗、金融和安全标准的具体承诺，须按客户实际适用规则另行核验。本版撤回旧文中统一而绝对的合规要求。

## 10. Web3 功能取舍

| 提议 | 当前决定 | 后续条件 |
| --- | --- | --- |
| Proof-as-a-Service | 保留，限定为可验证证据服务 | 证明导出、验证和用户价值 |
| 账户抽象 | 后置，不作为顺畅体验前提 | 用户确实需要控制链上账户或资产 |
| 可移植知识胶囊 | 保留普通格式设计 | 来源、版本、许可证、适用条件、测试与失效信息明确 |
| NFT 与知识交易市场 | 不进入当前交付路线 | 先证明合法授权、供需与交易价值 |
| Token 与真实性质押罚没 | 不进入当前交付路线 | 有可客观验证的违规行为、裁决与申诉机制 |
| x402 等支付协议 | 作为未来接口选项 | 有实际机器付费需求，而非为引入协议创造需求 |

ERC-6551 为 NFT 绑定账户，不自动赋予知识产权或版税。x402 提供 HTTP 付费访问，不自动解决内容许可和持续版税。

质押不能代替真假判断。测试失败可能来自环境、版本或前提变化，不应自动判定贡献者造假。当前防污染采用来源、适用范围、复现证据、冲突治理和撤销传播。

## 13. Agent 钱包化可行性与是否新立钱包项目评估

### 13.1 核心概念澄清：人类钱包 vs AI Agent 原生工作钱包的区别

* **传统 Web3 钱包（MetaMask / Phantom / OKX）**：面向人类，本质是**私钥容器与交互签名器**。其交互范式是被动等待人类在浏览器/手机弹窗中点击“确认”。一旦用于自主 Agent，人类确认弹窗会彻底打断自动化长任务。
* **AI Agent 原生钱包（Agentic Smart Account）**：面向自主程序，本质是**带预算门限（Budget Cap）、策略引擎（Policy Engine）与执行上下文（Context）的程序化授权账户（基于 ERC-4337 / Session Keys / ERC-7715）**。Agent 在人类预设的安全配额内自主调用外部付费 API、购买 GPU 算力、支付跨 Agent 协作酬劳。

### 13.2 能否做成钱包功能？（结论：完全可以，且是天然的上下文闭环）

`llm-workmem` 不仅能做钱包功能，而且能解决目前 Web3 钱包在 AI 时代的最大缺陷——**“有资产无上下文、有转账无因果”**：

1. **记忆与因果绑定的支出（Context-Bound Expenses）**：
   * 传统钱包转账只有 From/To/Value，不知道钱为什么花出去；
   * 结合 `llm-workmem` 后，每一笔支出必须关联明确的 `task_id`、决策理由（Decisions）与预期结果。交易哈希自动记录到周期回执（`CycleReceipt`）和项目记忆中，形成企业级的 AI 财务报销账本。
2. **基于验证证据的资金释放（Proof-Gated Escrow & Bounties）**：
   * 在多 Agent 协作或外包悬赏中，合约托管资金；
   * 只有当执行 Agent 在 `llm-workmem` 中产生通过测试的真实凭证（`verification: PASSED`），智能合约才释放资金，实现“验货才付款”。

### 13.3 是否值得做一个独立的“新钱包项目”？

对此必须做出绝对清醒的商业与工程定论：

| 方向 | 评估结论 | 原因与裁决 |
| --- | --- | --- |
| **做一个独立的通用人类 Web3 钱包（MetaMask 竞品）** | **坚决不做（严禁立项）** | 极度拥挤的存量红海，获客成本（CAC）极高，无核心壁垒，严重分散团队精力，必死无疑。 |
| **做一个独立的“AI Agent 专用的自主费用卡/智能账户项目”** | **不宜过早独立分拆** | 市场尚处于早期，单做 Agent 钱包缺乏高频使用场景与工作流黏性。 |
| **作为 `llm-workmem` 的二阶段/三阶段原生扩展模块** | **最佳战略路径（推荐）** | **以“工作记忆与上下文流转”为主干，以“Agent 钱包与支付”为延伸分支**。先通过免费记忆工具占领 11+ IDE 和终端，当 Agent 真正需要花钱买数据、租算力时，原生激活其内置钱包能力。 |

### 13.4 最终定位：从“工作记忆操作系统”演进为“AI 员工数字工牌与消费账户”

* **Stage 1（当下）**：跨 Agent 统一工作记忆与任务交接（解决日常开发上下文断层痛点）；
* **Stage 2（中期）**：团队记忆联邦与可靠备份/密码学存证（解决资产保全与可信协作问题）；
* **Stage 3（终局）**：Agent 自主经济与工单钱包模块（让 Agent 拥有属于自己的预算、数字身份与微支付能力，真正成为能够自主接单、自主买卖知识的独立生产力单元）。
